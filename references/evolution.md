# Experience-driven skill evolution

Use this guide to equip a skill to learn during use, or to improve SA itself. The executing agent performs the learning; Markdown alone does not run in the background. Reuse the host's existing tools and authorized storage, not a second memory service.

## Build a usable loop, not a reminder

When creating or substantially improving a target skill, connect these decisions to its real work:

- **Signals:** meaningful user corrections, verified non-obvious solutions, successful alternatives, recurring friction and counterexamples. Ordinary success needs no learning record.
- **Owner and scope:** locate the maintained skill and its writable scope. Keep project-specific facts in the project; attach reusable methods to the relevant skill topic. Upstream-managed skills need an authorized local experience location or an upstream proposal, not silent cache edits.
- **Experience:** retain the observation, why the approach mattered, applicable conditions and a small evidence pointer. Mark uncertain explanations as candidates. Keep private task details in their original records; a portable lesson must stand without copying transcripts or secrets.
- **Next use:** put a short retrieval cue at the decision the lesson informs. Reuse an existing topical reference; create an experience file only if it has a real reader. Do not inject the entire history on every run.
- **Revision and check:** decide whether the cause calls for changed guidance, a reference, a script, discovery repair or no change. Exercise the changed behavior and preserve an earlier version or focused diff. Later relevant work can confirm, narrow or contradict the lesson.

These are design questions, not mandatory headings or fields. A small skill can express the loop in a paragraph and its existing references. State the concrete feedback source, writable destination and retrieval cue in the resulting skill; do not leave them as generic placeholders.

A target should be able to use its own loop without calling SA for every lesson. Routine scoped maintenance can proceed under existing authorization. A read-only task remains read-only: give a candidate revision or use an already-authorized task record instead. Changing permissions, collecting new data, publishing or deploying elsewhere requires its own authority.

## Keep experience separate from adopted guidance

Raw task evidence, interpreted experience and current guidance have different jobs; they need not have three new directories. Existing task artifacts retain the evidence, topical notes retain useful explanations and counterexamples, and the skill carries the current method.

Before adopting a lesson, inspect the evidence and competing explanations. A user's explicit preference establishes that preference within its scope; it does not prove an empirical claim. One verified interface correction can justify an immediate fix. Repetition alone, retrieval frequency and model confidence do not prove correctness.

When a candidate does not help, retain useful evidence without installing the candidate as guidance. Do not manufacture an update to satisfy a quota. When evidence contradicts an old lesson, reconcile its scope and cause rather than append an opposite instruction. Consolidation, simplification and withdrawal of invalid guidance are valid outcomes; preserve user-required capabilities and history under the target's rules.

## Compile a small change and test the right thing

Use [Evaluate](evaluate.md) to distinguish discovery, actual use and task quality. Prefer a focused revision over a rewrite of the whole skill. Record the reason and applicability in the existing appropriate place, not a universal new ledger.

For a substantive method change, compare inspectable task artifacts under equivalent inputs, tools and requirements. Use real tests where available, or an explicit qualitative comparison for writing and research. Inspect regressions as well as gains; an aggregate score must not hide a broken user requirement. A failed tool or evaluator is not a low task-quality score. Simulation and model judgment must be labeled as such.

On subsequent relevant use, ask whether the lesson was retrieved, changed the decision, prevented the original problem or added avoidable work. Update the existing experience when the answer is informative. No scheduled monitoring, fixed run count, new role team or numeric confidence threshold is required.

## SA uses the same mechanism

At the start of authoring work, consult the relevant existing authoring/evaluation guidance and topic-specific experience, not every past record. When a meaningful authoring signal occurs, use the task's actual diff, result and feedback to diagnose it. Within authorized maintenance, revise the implicated SA guidance and check the changed behavior; otherwise preserve a scoped candidate in the task record.

Feedback from a target skill can improve SA's design method, but business-specific lessons stay with that target. For example, if a research skill mistakes short default output for removal of detailed reports, fix that skill's routing; if SA caused that design mistake, improve SA's capability-preservation guidance too. Do not copy the report's subject into SA or automatically rewrite every skill it previously produced.

Complete the current delivery before starting another optimization cycle. Do not recursively revise the evolution method just because it was used. Reopen it when actual outcomes or explicit corrections justify a change.

## Design references and limits

These are source-inspected design inputs, not installed dependencies or proof of improvement:

- [WikiSkill entry](https://github.com/Stahl-G/wikiskill/blob/da6984caca09d5f81b2336cf3067b59c0c18bb1e/skills/wikiskill/SKILL.md): experience, interpreted knowledge and candidate skills are distinct; rejected candidates need not erase useful learning.
- [Claudeception successor](https://github.com/abhattacherjee/claude-code-skills/blob/dcf81fd840d04ed934c12b0c56ffb966ae3b789a/plugins/skill-kit/skills/extract/SKILL.md): extract verified non-obvious lessons and search existing owners before creating skills.
- [Anthropic skill-creator](https://github.com/anthropics/skills/blob/dbd4588f9e1033efb41dad4bef2f7947c8993d44/skills/skill-creator/SKILL.md): compare meaningful outputs; description-trigger optimization is not task-quality optimization.
- [ACE curator](https://github.com/DannyMac180/ACE/blob/11e57e59250f85bb853f311059958be4f70794c9/ace/curator/curator.py): bounded updates instead of whole-context rewriting; semantic similarity alone cannot authorize factual replacement.
- [Pi continuous learning observer](https://github.com/opsCoffee/pi-continuous-learning-v2/blob/1be665cc7bfe49377780753f1c6aa8164845acc0/lib/observer.ts): host events can trigger learning, but self-rated confidence is not verification. Its capture and model calls are not enabled by adopting this method.
